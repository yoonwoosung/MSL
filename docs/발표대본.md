## 슬라이드 2 — 문제 제기

## 왜 머신러닝으로 DDoS를 탐지하는가?

**(1) 넣을 내용**
- DDoS란: 다수 출처가 대량 트래픽으로 서비스를 마비시키는 공격.
- 왜 ML인가: 규칙 기반(시그니처)은 새로운 공격 패턴에 약함 → 트래픽 '행동 패턴'을 학습해 미지의 공격도 탐지.
- 전공 연계: 정보보안 / 네트워크 침입탐지시스템(IDS)의 핵심 기술.
- 분류 문제 정의: 입력 = flow 단위 통계 특성, 출력 = 정상(0)/공격(1).

**(2) 캡쳐할 파일/코드 위치**
- `main.py` 1~9줄: 상단 docstring + 파이프라인 흐름 주석
  - 캡처 추천 표시: "전처리 → 비교 → 학습 → 평가" 키워드에 강조색 밑줄

**(3) 발표 대사**
- **문제 정의 → ** "정상 트래픽과 공격 트래픽을 구분하는 이진 분류 문제로 정의했습니다."
- **왜 ML → ** "규칙 기반은 알려진 공격만 막지만, ML은 트래픽의 '행동'을 학습해 변형 공격에도 대응할 수 있습니다."
- **전공 연계 → ** "이건 곧 침입탐지시스템(IDS)의 핵심으로, 보안 전공의 실제 문제입니다."

## 슬라이드 6 — 전처리 ★핵심★

## 식별자 제거 = 데이터 누수 차단

**(1) 넣을 내용**
- **누수의 정체**: 첫 버전은 `select_dtypes(np.number)`로 '숫자 컬럼 전부'를 학습에 사용 → IP·Port가 숫자로 저장돼 그대로 feature로 들어감.
- DDoS 데이터는 한 공격 IP가 수천 row 생성 → 같은 IP가 train/test 양쪽에 등장 → 모델이 '행동'이 아니라 '공격자 명단(IP)'을 암기.
- **수정 1**: 식별자 컬럼을 **명시적으로 drop** — *숫자여도 무조건 제거*.
- **수정 2**: 스케일러는 **train에만 `fit_transform`, test는 `transform`만** → 테스트 정보가 학습에 새지 않음.

**(2) 캡쳐할 파일/코드 위치**
- **캡쳐 1**: `modules/preprocessing.py` 38~48줄 — `_drop_identifier_columns()` 전체
  - 함께 보여주면 좋음: 27~35줄 `ID_COLUMNS`
  - 추천 표시: `ID_COLUMNS`, `to_drop`, `_drop_identifier_columns()`에 굵은 박스
- **캡쳐 2**: `modules/preprocessing.py` 108~111줄 — 스케일러 누수 방지
  - 핵심 코드: `fit_transform(X_train)` / `transform(X_test)`
  - 추천 표시: `fit_transform`과 `transform` 차이에 대비 화살표
- **캡쳐 3**: `python main.py` 실행 후 아래 로그
  ```text
  [누수 방지] 식별자 컬럼 제거: ['Source IP', 'Dest IP', 'Source Port', 'Dest Port']
  [범주형 인코딩] LabelEncoder 적용: ['Highest Layer', 'Transport Layer']
  ```
  - 추천 표시: 제거된 컬럼 리스트에 빨간 박스

**(3) 발표 대사**
- **누수 정의 → ** "데이터 누수란, 실전에선 쓸 수 없는 정답 단서가 학습에 흘러든 상태입니다."
- **원인 → ** "IP·포트가 숫자라서 `select_dtypes`가 못 걸렀고, 모델은 트래픽이 어떻게 생겼는지가 아니라 '이 IP가 공격자냐'를 외워버렸습니다."
- **해결 → ** "그래서 식별자를 명시적으로 지우고, 스케일러는 train에만 학습시켜 테스트 정보가 새지 않게 했습니다."
- **한 문장 요약 → ** "모델에게 '주소'가 아니라 '행동'만 보게 만든 겁니다."

## 슬라이드 13 — 튜닝 한계

## 튜닝 효과는 작았지만, 의미 있는 발견이었다

**(1) 넣을 내용**
- Lecture 10 기반 5개 파라미터 GridSearchCV 탐색:
  - `n_estimators`, `max_depth`, `min_samples_split`, `min_samples_leaf`, `max_features`
- **정규 탐색**: 48조합 × 3-fold = 144 fits
  - 최적: `n_estimators=100, max_depth=10, max_features=sqrt, min_samples_leaf=1, min_samples_split=5`
  - Best CV F1: 0.9981 / Test Accuracy: 0.9979 / Overfit gap: 0.0005
- **극단적 탐색 검증** (`experiments/extreme_tuning.py`): 80조합 × 3-fold = 240 fits
  - 최적 Test F1 0.9980 vs 기본값 0.9979 → **차이 0.0001**
  - 최악 조합(`max_depth=2`) CV F1: 0.9632
- **고찰 — 튜닝 효과가 미미한 이유 3가지**:
  1. 특성 4개 → `sqrt(4) = log2(4) = 2`로 `max_features` 두 옵션이 수치상 동일
  2. 훈련 데이터 68만 행 → 어떤 설정이든 수렴
  3. RF 배깅 구조가 개별 트리 설정 차이를 흡수

**(2) 캡쳐할 파일/코드 위치**

  - 추천 표시: `max_depth`, `max_features`, `min_samples_leaf`, `n_estimators` 강조
- **캡쳐 2**: `python experiments/extreme_tuning.py` 실행 후 출력
  ```text

  [튜닝 후 Test F1] 0.9980
  [차이] 0.0001

  [최악 조합]
    n_estimators=10, max_depth=2, min_samples_split=2
    CV F1: 0.9632
  ```
  > ※ GridSearchCV verbose 로그가 먼저 수백 줄 출력되므로, **터미널 맨 아래로 스크롤** 후 위 부분을 캡쳐
