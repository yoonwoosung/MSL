## 7슬라이드 — 데이터 전처리 파이프라인

**역할**: 일반적인 전처리 흐름 설명, 누수 발견의 복선 깔기

**슬라이드 내용**

모델 학습 오류를 방지하고, 데이터를 학습 가능한 형태로 변환하기 위해 전처리 파이프라인을 구축하였다.

- **Feature Selection** — 비수치형·불필요 컬럼 정리 / 초기에는 숫자형 컬럼 중심으로 학습 데이터 구성
- **Label Encoding** — target 값을 정상/공격 → 0/1로 변환
- **Data Cleaning** — 결측치, 무한대 값 제거
- **Data Split** — Train 80% / Test 20% / stratify로 클래스 비율 유지
- **Feature Scaling** — StandardScaler 적용 / 특성 간 단위 차이 보정

> 하단 강조 문장: 이후 100% 정확도가 나타나면서 전처리 과정의 데이터 누수를 추가로 점검하였다.

**대본**
"먼저 모델이 데이터를 안정적으로 학습할 수 있도록 전처리 파이프라인을 구성했습니다. 정답 레이블은 0과 1로 변환했고, 결측치와 무한대 값은 제거했습니다. 이후 데이터를 학습용 80%, 테스트용 20%로 나누고, 클래스 비율이 유지되도록 stratify를 적용했습니다. 또 Packet Length나 Packets/Time처럼 단위 차이가 있는 변수는 StandardScaler로 보정했습니다. 그런데 이 전처리 이후 모델 정확도가 100%로 나타났고, 이를 계기로 데이터 누수 가능성을 확인하게 되었습니다."

## 8슬라이드 — 데이터 누수 발생

**역할**: 반전, 100%가 왜 문제인지 설명

**슬라이드 내용**

제목: 100% 정확도의 원인: 데이터 누수

- 사진: 전처리 후 정확도 100% 캡처 + 원인 코드 (`feature_importance_kaggle.png` 또는 100% 혼동행렬)
- 핵심 문장: 전처리 후 정확도 100%가 나타났고, 이를 비정상적인 결과로 판단하였다.
- 원인:
  - 숫자형 컬럼 자동 선택
  - 숫자로 저장된 IP/Port가 학습에 포함
  - train/test에 동일한 공격자 IP 반복 등장
  - 모델이 트래픽 행동이 아니라 식별자를 암기
- 강조: **100%는 성능이 아니라 정답 단서를 외운 결과였다.**

> 💡 캡처 추천: `feature_importance_kaggle.png` (루트 폴더) — Source IP가 중요도 1위(0.44)로 나오는 그래프. "모델이 IP를 보고 판단했다는 직접 증거"로 사용.

**대본**
"처음 전처리를 마친 뒤 모델을 학습했을 때 정확도 100%가 나왔습니다. 처음에는 좋은 결과처럼 보였지만, 보안 트래픽 데이터에서 100%는 오히려 비정상적인 신호라고 판단했습니다. 원인을 확인해보니 IP와 Port 같은 식별자 정보가 숫자형 컬럼으로 인식되어 학습에 포함되어 있었습니다. 결국 모델은 Packet Length나 Packets/Time 같은 행동 패턴을 학습한 것이 아니라, 특정 IP가 공격자였다는 사실을 외운 것이었습니다."

**대본**
"따라서 실전에서 사용할 수 없는 Source IP, Destination IP, Port 정보를 명시적으로 제거했습니다. 이후 모델은 식별자가 아니라 Packet Length와 Packets/Time 같은 행동 특성을 중심으로 학습하게 되었습니다. 그 결과 정확도는 100%에서 99.79%로 낮아졌지만, 오히려 이 값이 실제 성능에 가깝습니다. 즉, 100%는 IP를 외운 결과였고, 99.79%는 트래픽 행동 패턴을 학습한 결과라고 볼 수 있습니다."

## 11슬라이드 — 하이퍼파라미터 튜닝

**역할**: GridSearchCV로 최적 파라미터 탐색, 기본값이 최적임을 실험으로 검증

**슬라이드 내용**

제목: 하이퍼파라미터 튜닝 결과

- 탐색 방법: GridSearchCV (5개 파라미터, 48조합 × 3-fold = 144번 학습)
- 추가 검증: 극단적 조합 80가지 추가 실험 (총 128가지 조합)

| 구분 | F1 점수 |
|------|:-------:|
| 기본값 | 0.9979 |
| 튜닝 최적값 | 0.9980 |
| **차이** | **0.0001** |

- 튜닝 효과가 미미한 이유:
  1. 특성 4개 → `√4 = log₂4 = 2`, max_features 두 옵션이 수치상 동일
  2. 68만 행 데이터 → 어떤 설정이든 수렴
  3. RF 배깅 구조가 파라미터 차이 흡수

- 강조: **튜닝을 안 한 것이 아니라, 128가지 실험으로 기본값이 최적임을 검증한 것이다.**

> 💡 캡처 추천: `modules/tune.py` param_grid 코드 부분 (n_estimators, max_depth 등 파라미터 목록 보이게)

**대본**
"기본값이 최선이라는 보장이 없기 때문에 GridSearchCV로 48가지 조합을 탐색했습니다. 추가로 극단적인 파라미터 80가지를 더 실험했는데, 총 128가지 조합을 돌려도 기본값과 F1 차이가 0.0001에 불과했습니다. 이는 특성이 4개뿐이라 파라미터 옵션이 수치상 동일해지고, 68만 행의 대용량 데이터에서는 어떤 설정이든 수렴하며, RandomForest의 배깅 구조 자체가 파라미터 차이를 흡수하기 때문입니다. 결론적으로 튜닝을 안 한 것이 아니라, 실험을 통해 기본값이 이미 최적임을 확인한 것입니다."

## 13슬라이드 — 재현성 & 마무리

**역할**: 신뢰성 강조 및 프로젝트 핵심 메시지로 마무리

**슬라이드 내용**

제목: 재현성과 프로젝트 정리

- 재현성:
  - 모든 모델·분할에 `random_state=42` 고정
  - 동일 환경이면 누구나 같은 결과 재현 가능
  - 최종 모델 `final_model.pkl` 저장 (joblib)

- 코드 구조:
  ```
  preprocessing.py  →  식별자 제거, 스케일링
  train.py          →  RandomForest 학습·저장
  evaluate.py       →  모델 비교, 시각화
  tune.py           →  GridSearchCV 튜닝
  ```

- 한계 및 향후:
  - 단일 데이터셋 검증 → 다른 환경 일반화 미확인
  - 실시간 탐지 연결 시 추가 개발 필요

- 마무리 문장: **이 프로젝트의 진짜 결과는 99.79%가 아니라, 100%가 왜 틀렸는지 알아내고 신뢰할 수 있는 성능을 만든 과정입니다.**

**대본**
"모든 실험에 random_state를 42로 고정했기 때문에, 채점하실 때도 동일한 결과가 재현됩니다. 마지막으로 이 프로젝트에서 저희가 가장 중요하게 생각한 것은 수치 자체가 아닙니다. 100%라는 결과를 의심하고, 원인을 찾고, 신뢰할 수 있는 성능을 만든 과정이 핵심이었습니다. 감사합니다."
